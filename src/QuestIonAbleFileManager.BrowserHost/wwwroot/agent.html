Agent guide

No headset app is required for these ordinary ADB operations. Developer mode, headset debugging authorization and an accessible transport are still prerequisites.

Install and offline use

Use the browser menu to install QFM or add it to your home screen where supported. After one online load, the app shell and this guide remain available offline. Live device commands need a running local connector. Tokens, API results, files, APKs and captures are never cached by the service worker. Changes are never queued for reconnect. Offline status clears the host connection; reconnect explicitly, read current state and reconcile any original unknown request before another change.

The connector address belongs to this computer. Opening localhost on a phone does not connect it to your PC. Direct WebUSB is an optional browser capability; use the qualified CLI/local connector when browser USB is unavailable or already owned by shared ADB.

QFM host

The optional BrowserHost serves this interface and a closed same-origin API. Start it explicitly with the configured ADB executable and private session token. Connect using that token, refresh devices, select an exact ready target and read its status. The token remains in tab memory and is cleared on disconnect; it is never part of a URL or browser storage.

WiFi setup and device settings require the matching approval checkbox. Coordinate the actual device slot and supervisor custody first. A confirmed receipt requires operation-specific effective readback; HTTP success alone is not confirmation. Do not automatically repeat a pending or unknown mutation. Use “Read original result” with the retained request ID. A host restart invalidates its session; retain uncertainty and inspect current state before selecting any recovery through the documented owner route.

The browser host invokes the same immutable OperatorCommand and Core executor used by QFM CLI. The browser supports device/status, WiFi enable/connect/disconnect, awake/normal and CPU/GPU controls, directory browsing, package/permission views, actor observations and forward inventory. Read-only file pulls and single-APK exports use bounded Core streams. File upload/push uses an explicit full destination and overwrite approval. Advanced APK, remaining Kiosk controls/Direct Link and Fleet migration remain documented work. The chosen duration bounds the proximity hold; stay-awake remains enabled until an explicit Restore normal change. It does not expose raw shell, a generic command runner, Fleet authority or a new watchdog.

Local APK inspection

On a Windows host with a local NTFS temporary volume, choose an APK, stage its bytes and inspect its package, version and signer through the same Core inspector as the CLI. Android Build Tools and their Java runtime must be configured on that host. The connector validates private permissions and immutable file handles before admitting a staging root; platform support alone is not readiness.

Uploads are limited to 1 GiB each, 8 files and 2 GiB in this process; connected capabilities report the actual numerical limits. Transport and verification have a five-minute bound. Save opens the supporting browser file picker directly, verifies streamed size and SHA-256 before closing, and aborts incomplete output. Other browsers use a verified buffered download only up to 256 MiB; larger files need streaming Save or the CLI. A browser download handoff does not prove final disk-save completion. Remove/Clear affects only owned unleased temporary files; original files are unchanged. Staged references remain in tab memory and are invalid after host restart. Lost upload responses never retry automatically. Use explicit Clear staged files after reconnecting to recover capacity. Correct a failed temporary-root configuration before restarting the connector, and handle any unresolved device request before that restart.

Linux/macOS explicitly report protected path staging unavailable; use the Windows companion or current QFM desktop/CLI for those operations. API results, APK bytes and private paths never enter the offline shell cache.

Upload and push a file

Choose and stage a file in the separate upload view, select one ready headset and enter a full absolute destination filename. Review the staged bytes, target and destination, then explicitly approve overwriting an existing file. Approval resets when those choices change. The connector holds an immutable source lease through the existing Core push and observed destination-type/size checks. Confirmed means remote size only; it proves neither remote SHA-256, atomic publication nor recovery of overwritten bytes.

The small original reference is saved before execution. A lost, pending or crossed reply blocks further device changes; reload and reconnect never resend. Read the original result explicitly using its recorded session and request, even if the current target changed. Host restart loses that transient ledger, so preserve the reference and use the typed owner recovery route. Removing a staged source never clears an unknown write. Upload receipts remain separate from APKs, downloads and Native operations; API bytes and credentials never enter the offline cache.

Read-only file downloads

Select one ready target and one full headset file path, then Stage download. Single-APK export uses one exact installed package, rejects splits before streaming and returns captured-byte SHA-256/checksum text. Export copies neither app data, assets nor entitlement. Core reads one opened regular remote file, enforces the byte ceiling and completion evidence, then the private store independently verifies the output. Captured bytes are not an application snapshot or runtime readiness.

Review the capture target, source, name, size and digest before Save. Remove affects only that exact owned local capture. Capture references stay in tab memory, separate from staged local APKs and retained operations; new host sessions invalidate them. Lost capture replies never replay automatically and can leave bounded local bytes for explicit Clear. Streaming Save needs browser file-picker support and user activation. Cancelled or uncertain close/cleanup is not successful save confirmation; check the selected file before trying another save. API bytes and credentials never enter the offline shell cache.

APK readiness and runtime reads

Stage an APK and select one ready headset, then Read APK readiness for Core SDK compatibility, installed-byte classification, exported launcher and deploy/launch/diagnose checks. This is separate from preparing a retained effect. Observe exact installed APK requires exact installed bytes; absence is structured and mismatch never falls back automatically. Observe matching development metadata is an explicit weaker choice: matching package/version/path/update facts prove neither installed bytes, signer, unique build nor transaction provenance. Both policies leave application and OpenXR readiness unknown.

These reads need no Native API state/key configuration. They hold the current source lease through Core completion and a path-sanitized projection. Source, target, policy or authentication changes clear displayed facts and reject late replies. No read is stored or replayed, and it never clears an unknown original mutation or approves an effect. An explicit local connection can read USB ADB while the wider network is offline.

Retained APK workflow

On Windows, configure the existing Local API state directory and private journal integrity key for this connector. Preserve both across restarts. Another process owning that state must be handled through its normal lifecycle; a fresh directory or key must never bypass uncertainty. The browser bearer is separate, and this projection opens no second API listener.

Stage an APK, select a ready headset, prepare an inspected install, resolved launch, exact single-target deploy or runtime observation, then review the exact bytes, package, version, signer, target, options and expiry before approving one execution. The retained owner makes its own protected copy. Source removal requires explicit original status before approval; a different selected APK blocks approval. Default approval lasts two minutes, at most five. Install and exact deploy support replace-existing and permission grants. Deploy installs exact bytes and launches the resolved component once; owner completion does not establish app/OpenXR readiness. Splits, downgrade, test-only and diagnostic workflows remain with the typed CLI.

Exact deploy requires the explicitly advertised v2 contract. Its original reference retains that version; manual recovery requires selecting it explicitly. Legacy references remain v1. Every original status/cancel/execute follows its saved version, never the current operation choice. V1 and v2 share the same journal/key; older owner binaries reject v2 rows, so preserve the qualified current owner for recovery. Save the original version, ID and digest promptly. Only a small reference enters tab session storage; owner terminal records, including unknown outcomes, have a bounded 24-hour retention. Reload and authentication send no operation. Read original status or request cancellation of running work explicitly; neither proves a dispatched effect was absent. An unexecuted prepared record must expire, followed by explicit status; v1 cannot cancel it. An unknown original keeps mutations blocked. Never repeat it. Separate Observe selected runtime preserves that original and reports later facts through its own saved reference. These facts do not rewrite the original receipt or establish app/OpenXR readiness. Preserve the original journal and use the typed owner recovery route.

Optional Kiosk catalog

Select an exact ready target and Stable or Labs channel. Passive installation reads fixed package/control-contract facts without requesting Kiosk activity; flags and versions are not fresh signer, connectivity or application-readiness evidence. Opening the catalog and selecting a returned installed, launchable row require their own explicit consent and may request Kiosk activity. Local filtering and highlighting send nothing. This card sends no app-launch command and does not establish foreground or app readiness.

Only a unique eligible key/package from a completed catalog in this host session can be selected. Replies bind the saved target, channel, provider ID and Core marker; conditional installation-only unavailability reports no catalog or selection. Pending or unknown outcomes keep other mutations blocked. The request and pc-provider IDs are saved before execution; reload/reconnect never replay. Read original browser result uses its existing ledger only. Separate provider facts never admit or open Kiosk and never clear an unknown original, even if they later report completion. A changed host session loses its transient ledger; save the reference for the typed owner recovery route. Incomplete provider replies do not prove missing requests or no effects.

Kiosk outputs are bounded and catalog truncation is explicit. No catalog/result/credential is stored in the offline cache or tab storage. Native API state/key and protected staging are unnecessary for this card. Direct connection controls are described below. Launch/options, setup/provisioning, tag transport and secondary controls retain the qualified CLI/WPF alternative.

Optional USB Direct connection

Explicit connect binds one ready classic USB target and Stable/Labs product. The host completes existing USB bootstrap, signed status, typed Kiosk Status and staging-inventory adoption before publishing an opaque handle. The endpoint, session key and private session/generation remain native. Connected means authenticated operator transport, not app foreground or readiness. This card has no launch, generic command, file or install action.

Read signed status and close are explicit and remain bound to the saved connection target/channel. An owned listener is confirmed disabled and stopped; a pre-existing listener is preserved. Cleanup uncertainty stays separate from the original request. Expiry erases the key and blocks use of the handle; explicit close still handles its nonsecret cleanup custody. Orderly host shutdown awaits cleanup. Keep the host and USB transport available for that acknowledgement.

Only small nonsecret original/connection references enter tab session storage. They are saved before effect dispatch; reload/authentication/expiry never reconnect, close or replay. Unknown connect/close responses block further device changes. Same-session original GET can recover its actual acknowledgement; signed status and expiry do not reconcile that original. A changed host cannot restore the key or transient ledger, and this slice supplies no saved-ID restart cleanup API. Save the reference for owner investigation. Never issue a new connect to infer the old result.

Local Windows connectivity profiles

The profile card manages only current-user File Manager connectivity records. Refresh IDs, check stored validity, create/import, replace and revoke are explicit. A stored enrolled record is parsable configuration, not a connected or ready headset. Revoke removes the local record; it does not stop a listener or revoke a remote credential. No ready target, ADB, staging, Native retained configuration or Fleet installation is needed. Other platforms use the Windows companion/CLI alternative.

Private fields or a selected JSON file go only to the bounded sensitive import route using the existing owner enrollment format and exact reviewed device ID. Creation does not grant replacement authority. Replacement and revoke have separate exact-ID approval. Exact Core write/readback or confirmed rollback can acknowledge that original; uncertain rollback or delete readback remain unknown. New status, including enrolled or absent, never confirms the identity of a lost secret write.

Private USB, endpoint, code, File and owned document bytes clear after attempts, cancellation, authentication and visibility changes. Only a small nonsecret original request/session/action/device-ID/replacement reference enters tab storage; private input never enters staging, result views or offline caches. Reload and reconnect send no operation. Read the original browser result explicitly; a restarted host cannot recreate its old transient ledger. Preserve unknown references for owner investigation. Native credential-store calls finish verification or rollback before their gate and private input are released; orderly shutdown drains admitted changes. The Windows store protects the current-user boundary, not isolation from other processes of that user.

USB proof

Use a WebUSB-capable desktop browser in a secure context, including localhost. Windows needs a compatible USB driver/interface association. “Choose USB headset” opens the browser chooser; headset RSA authorization can require physical access. These prompts may be outside a browser agent's DOM and need a human. A browser backend without USB access must report unavailable rather than bypass permissions.

This mode uses pinned Tango packages bundled locally to read fixed serial/boot/battery facts, with explicit handle selection. It never changes power, transport or installed packages. An interface already held by shared ADB can be busy. Keep the shared daemon and existing watchdog running; use host mode instead of killing it.

Authentication keys are retained in this browser origin's IndexedDB by Tango. Disconnect releases the connection but retains the key. Clearing this origin's site data removes the local key; revoking debugging authorizations on the headset is a separate protected action. A folder on a shared origin is not an isolated permission boundary.

Typed alternatives

When browser permission or UI automation is unavailable, use the selected qualified QFM CLI with its configured ADB. These are the same owner implementation's ordinary routes:

questionable-file-manager.exe devices --json
questionable-file-manager.exe device status --serial <exact-target> --json
questionable-file-manager.exe wifi connect --host <known-host> --port 5555 --confirm-wifi-adb --json
questionable-file-manager.exe device keep-awake --serial <exact-target> --on --duration-ms 3600000 --confirm-device-settings --json

Read nested mutation/result fields and preserve pending outcomes. Shell exit zero is insufficient. Ordinary keep-awake does not enroll a device or adopt Fleet scheduling. Changes through CLI require the same real target authority and current custody as browser actions.
